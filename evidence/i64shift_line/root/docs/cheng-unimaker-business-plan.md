# Cheng 语言 + UniMaker 商业计划书

> 版本：2026-07-11 草案。数据口径见文末"数据来源与诚实性声明"。

## 一、执行摘要

Cheng 是一门从零自举的系统级编程语言，目标是"比 C 更快、比 Rust/Swift 更简单、原生支持多端后端"。截至目前，Cheng 已经跑通完整自举链（种子编译器 → Stage1 → Stage2 → Stage3），不动点哈希锁定为 `e202c0c35424eb36`，回归门禁 `ci_gate` 从最初 9 项扩展到当前 35 项全部通过。UniMaker 是建立在 Cheng 之上的跨端应用制作器，面向不依赖大团队的个体创作者，主打"秒发秒开"（内容/应用一次发布、各端毫秒级唤起）和从 React 生态迁移应用的能力。

我们的核心判断：跨端开发的碎片化（一套逻辑写三遍：iOS/Android/Web）和性能税（脚本引擎/虚拟机层层损耗）是老问题；AI 时代放大了个体创作者的产能，但现有工具链（小程序框架、Flutter、AI 应用生成器）要么锁定在某个平台，要么牺牲性能换取开发速度。Cheng+UniMaker 想做的是：用一门自举、确定性内存管理、可被 AI 高效生成和验证的语言做底座，把"一次开发、多端原生性能、AI 辅助生成"三件事同时做到。

现状要如实说：语言底座的自举与正确性验证已经过硬（自举不动点稳定、大量 exec_diff/census 交叉验证网），但 Cheng 距离"零 C 依赖"（彻底去掉冷启动用的 C 运行时）尚未完成，热路径性能相对冷路径仍有约 229 倍差距，这是当前最大的技术攻坚点。UniMaker 侧，核心链路（秒开、Android 双端真机验证、部分 React 迁移能力）已有实测数据支撑，但 1:1 功能对齐和公测尚未完成。本计划书的定位是：基于已验证的技术资产，规划下一阶段的产品化和商业化路径，融资将主要用于补齐性能攻坚和生态冷启动两个缺口。

## 二、问题与机会

**问题一：跨端开发碎片化。** 一个创作者想做一个"发布内容、多端秒开"的应用，今天仍要面对 iOS/Android/Web/鸿蒙 至少三套技术栈、三套构建流程、三套性能调优经验。中间层框架（RN、Flutter）缓解了部分问题，但引入了额外的运行时和"最终一致但不原生"的体验代价。

**问题二：性能税。** 脚本引擎、虚拟机、GC 停顿、跨语言桥接（JS↔Native）是移动端体验（尤其是首屏秒开、大文件传输、音视频编解码、加密握手）的隐性成本。多数应用层框架选择"用户体验可接受就行"，很少有团队愿意从语言和后端代码生成层面重新设计以彻底消除这层税。

**问题三：AI 时代个体创作者产能被工具链拖累。** 大模型让一个人能设计、写代码、测试的产出量级远超从前，但"发布到多端原生应用"这一步仍然需要平台专业知识（签名、构建链、性能调优、协议栈）。这部分知识密集、试错成本高，恰恰是 AI 生成代码最容易踩坑、也最需要一个"设计上就对、AI 改了也不容易错"的底座去兜底的地方。

**机会：** 如果有一门语言从设计上保证内存确定性（无 GC 停顿）、自举验证（编译器本身可自证正确性）、且配套一个把"多端发布"做成一次点击的制作器，AI 生成的代码 + 这套底座，能让个体创作者获得过去需要中大型团队才能做到的原生多端性能和分发效率。这不是"更好用的 Flutter"，而是从语言层重新定义"一次编写、原生多端、AI 友好"的组合。

## 三、产品线

### 3.1 Cheng：系统级语言底座

Cheng 定位为可自举、确定性内存管理、面向多端后端代码生成的系统级语言，是 UniMaker 的技术地基，也可独立作为通用系统语言使用。

已验证的技术事实：
- **自举闭环**：种子编译器（C 实现）→ Stage1 → Stage2 → Stage3，不动点确认（`e202c0c35424eb36`），意味着 Cheng 编译器可以用 Cheng 自己写的代码编译自己，且结果稳定收敛，这是编译器工程里验证语言"设计自洽、实现无隐藏缺陷"的硬指标。
- **回归门禁**：`ci_gate` 目前 35 项检查全部通过（含确定性重复编译一致性、字节级产物对比、bootstrap 不动点校验等）；生产回归套件历史记录为 1346/1348（99.85%）通过。
- **多端后端**：已产出可用的 ARM64 后端代码生成（Android/鸿蒙真机验证过），配套自研网络协议栈（QUIC/TLS1.3、VPN 传输层）和加密算法实现（RSA-PSS、ECDSA、ChaCha20-Poly1305），全部是 Cheng 自己写的运行时代码，不依赖第三方 crypto/network 库。
- **性能现状（如实披露）**：语言团队用"beat-C"（目标是特定负载下不输给对标 C 实现）作为长期性能北极星。截至目前：① 自举保真度侧（Cheng 编译器跑冷路径 vs 原始 C 种子跑同任务）实测比值 0.78×，即用 Cheng 自己编译产出的编译器在这类任务上不比 C 慢，反而略快；② 真正的性能瓶颈在"热路径"（Cheng 后端自身生成代码的执行效率）相对"冷路径"（当前依赖的 C 运行时兜底）仍有约 229 倍差距，这是下一阶段重点攻坚对象；③ 增量编译（改一行代码只重新编译受影响部分）已经接线并生效，实测比全量重编快 5%-23%，尚未达到设计目标的数量级提升，仍在推进中。

这里的诚实立场是：Cheng 的"正确性"（自举、确定性、回归稳定）已经有扎实证据，但"极致性能"（完全甩开 C 依赖、热路径追平冷路径）仍是进行中的工程，不是已经兑现的产品卖点。

### 3.2 UniMaker：面向创作者的跨端应用制作器

UniMaker 建在 Cheng 之上，目标用户是不具备完整移动端工程团队的个体/小团队创作者，核心卖点：

- **秒发秒开**：内容/应用发布后各端能在极短时间内完成拉取和呈现。已有的实测数据：Android 真机双进程场景下，通过 hash 匹配实现 0ms 级别的内容命中拉取；一次端到端视频发布链路实测总耗时 944ms（在一个真实测试资产上达到"发布到可见 ≤1000ms"的内部目标）；同一链路上，通过把 TLS 握手中的证书签名算法从 RSA-PSS 换成 ECDSA，把冷启动握手耗时从 860ms 降到 560ms。这些都是在特定测试设备和资产上的真实测量，不是理论值。
- **React 生态迁移能力**：为了让存量 Web/React 应用能够低成本迁移到 Cheng 原生跨端体系，团队做了一个"React → Cheng"的转译器（CHT，复用已有的转译框架并做了运行时化改造）。据内部记录，目前功能覆盖率约 56%（在既定的组件/事件处理器样本集上），已明确剩余缺口（如运行时数据绑定的边界情况），不是宣称"已完成迁移"。
- **视觉与交互设计**："水墨"视觉体系（UniMaker v2 设计提案）已完成设计稿和分阶段里程碑规划（M1-M5），首页双卡片布局在 Android 和鸿蒙两端真机上做过交叉验证（互相发布内容、互相播放）。
- **跨端覆盖现状**：Android 端的秒发秒开链路和自研 VPN（per-app 代理）功能均已在真机跑通；鸿蒙端受限于系统权限模型（SELinux 策略对部分 CLI 能力的限制）和宿主生成链路仍在打通中，是当前跨端一致性的主要缺口。

## 四、技术护城河

我们认为真正难以复制的不是某个单点功能，而是四件事叠加：

1. **自举编译器本身即是护城河**：能把一门语言的编译器完全用该语言自己重写并稳定收敛（自举不动点），这是编译器工程里门槛最高的验证之一——它同时证明了语言表达力足够、类型系统和内存模型没有自相矛盾的角落、工具链可以长期自我维护而不依赖外部实现"背书"。多数新语言项目止步于"用 Rust/C++ 写一个还不错的编译器"，很少走到"能自己编译自己且结果确定性收敛"这一步。

2. **全栈自研网络与加密协议**：QUIC/TLS1.3、VPN 传输、RSA/ECDSA/ChaCha20 全部是自己实现，不是对接 OpenSSL/BoringSSL 之类第三方库做壳。这带来两个好处：性能瓶颈可以下探到算法内部（例如把签名算法从 RSA-PSS 换成 ECDSA、把点乘算法从 wNAF 换成固定窗口 comb6，实测握手耗时从 482ms 降到 424ms）；同时也意味着安全审计和长期维护责任完全自担，是双刃剑，需要在风险章节如实说明。

3. **AI 多智能体研发范式**：这个项目本身的研发过程大量使用多智能体协同（一个"主线"agent 负责架构决策，多个并行 agent 负责不同攻坚线，用共享的验证工具链——census/exec_diff/ci_gate——做交叉校验和"对抗式复核"）。这套研发范式本身被验证可以在没有大团队的情况下，维持一个百万行级代码库的正确性回归，这是团队规模效应的替代方案，也是我们相信"小团队也能做系统级语言+应用制作器"的组织基础。

4. **Fusion 工具链**：围绕 Cheng 开发了一整套配套诊断工具（CSG 结构化查询、崩溃分诊、字节级产物对比、符号回归检测等），这些工具不是"锦上添花"，而是自举语言在没有成熟第三方生态（没有现成的 LLVM/GDB/Valgrind 支持）情况下必须自己造的基础设施，也构成了后来者复制这条路径的时间壁垒。

## 五、市场与竞品

**语言层竞品**：Rust（安全性强，学习曲线陡峭，无自举历史包袱但生态成熟）、Zig（简洁、无隐藏控制流，但仍依赖 C 工具链做很多任务）、Swift（苹果生态强绑定，跨平台是后加的）。Cheng 的差异化不在"语法更好看"，而在"从设计起点就是多端后端 + 自举验证 + 面向 AI 生成友好"，这三者叠加目前没有直接对标者。

**应用制作器层竞品**：微信/支付宝类小程序框架（分发效率高但锁定单一平台生态、性能受限于宿主 JS 引擎）、Flutter（跨端体验好但仍是"渲染引擎抹平差异"而非原生代码生成，且 Dart 生态相对封闭）、Bolt/v0 类 AI 应用生成器（生成速度快，但产出通常是 Web/React 代码，仍要过一遍传统跨端框架才能变成原生应用，且不解决底层性能问题）。

UniMaker 的定位是"AI 生成的产出直接编译成多端原生代码，而不是生成后再套一层跨端框架"。这意味着 AI 生成效率 + 原生性能 + 多端分发三者同时具备，是我们认为目前市场上没有直接对标产品的组合。需要如实指出：这个定位能否被市场感知和买单，取决于产品公测后的真实转化数据，目前尚无付费用户数据支撑，这是待验证假设而非既成事实。

## 六、商业模式

**给出三个选项，推荐组合方案：**

- **选项 A：语言完全开源，无商业化。** 优点是生态冷启动最快、开发者信任度最高；缺点是没有收入支撑持续攻坚（尤其是性能攻坚需要长期投入）。
- **选项 B：语言开源 + UniMaker 订阅制 SaaS。** 个人/团队按月付费使用制作器（发布额度、高级模板、构建加速等分层）。优点是收入模型清晰、和"AI builder"类竞品的商业模式接近，用户容易理解。
- **选项 C：语言开源 + UniMaker 免费层引流 + 企业版（私有部署/性能 SLA/优先支持）+ 生态分成（模板市场、插件市场抽成）。**

**推荐：B + C 组合。** 逻辑是：语言本身开源建立开发者社区信任和贡献生态（这是自举语言项目获得长期生命力的前提，参考 Rust/Zig 的路径）；商业收入来自 UniMaker 这一层——面向个体创作者的订阅制满足现金流，面向企业客户的私有部署/性能 SLA 满足更大客单价需求，模板/插件市场分成作为生态成熟后的长尾收入。这个假设需要在公测阶段用真实转化率、留存率数据验证，目前是基于同类工具（AI 应用生成器、跨端框架）商业模式的类比推断，不是已验证的财务模型。

## 七、路线图

以仓库中真实的里程碑记录为骨架，不虚构未发生的进度：

| 阶段 | 内容 | 现状 |
|---|---|---|
| 点火（自举闭环） | 种子编译器 → Stage1/2/3 自举不动点 | **已完成**，不动点 `e202c0c35424eb36` 锁定，`ci_gate` 35/35 |
| 零 C 依赖 | 彻底去掉冷启动阶段依赖的 C 运行时/解析器 | **进行中**，冷路径覆盖持续扩大，尚未完全替换 |
| 性能达标（beat-C） | 热路径追平/反超对标 C 实现 | **进行中**，热/冷路径差距约 229 倍，增量编译已接线（提速 5%-23%），regalloc（寄存器分配）等深层优化在攻坚 |
| UniMaker 核心链路 | 秒发秒开、跨端真机验证 | **部分完成**，Android 双端实测达标；鸿蒙端受系统权限限制，宿主生成链路推进中 |
| React 迁移能力 | Web/React 应用迁移到 Cheng 原生跨端 | **进行中**，功能覆盖约 56%，边界场景待补 |
| UniMaker 1:1 对齐 | 六大子系统功能对齐设计稿 | **进行中**，剩余缺口已立卷跟踪 |
| 公测 | 面向真实创作者开放 | **未开始** |

下一阶段的两条主线：一是继续攻坚热路径性能差距（这是决定"Cheng 到底能不能兑现 beat-C 承诺"的核心工程问题）；二是补齐 UniMaker 1:1 功能缺口并推进鸿蒙端打通，为公测做准备。

## 八、团队与研发体系

当前研发以小规模团队 + AI 多智能体协同为主要模式：一名核心决策者把关架构和正确性标准，多条并行的 AI agent 攻坚线各自负责性能优化、正确性验证、产品功能等不同战场，通过共享的自动化验证工具链（回归门禁、字节级产物对比、崩溃分诊）做交叉校验，避免"看起来修好了但实际引入新错误"的假绿情况。这套体系已经在验证百万行级代码库的自举正确性上跑通，是本项目区别于传统"堆人力"研发路径的核心方法论资产。融资后的团队扩张方向：补充系统语言编译器/后端优化的专业人才（应对热路径性能攻坚），以及产品/增长人才（应对 UniMaker 公测和商业化）。

## 九、财务假设与融资用途

**声明：本节所有数字均为规划假设，不是已发生的财务数据或市场调研结果，目的是给出推算逻辑框架，供后续用真实调研数据替换。**

市场规模推算逻辑（TAM/SAM/SOM 框架，非实测）：
- TAM（总量假设）＝全球独立开发者/小型创作团队中，有跨端发布需求且愿意为工具付费的群体规模 × 年均工具支出。这个数字需要通过第三方市场报告（如开发者生态调研、低代码/AI 应用生成工具市场规模报告）交叉验证后才能给出可信数字，本计划书不做未经验证的具体数值假设。
- SAM（可服务市场）＝TAM 中对"原生多端性能"有明确诉求、且能接受从 Web 框架迁移到新工具链的子集，通常是 SAM 显著小于 TAM，需要通过公测阶段的用户访谈和转化数据校准。
- SOM（可获得市场）＝取决于公测后 12-24 个月的获客能力和产品完成度，在没有公测数据之前给出具体百分比是不负责任的，本计划书不做假设性数字填充。

融资用途结构（按优先级）：
1. **性能攻坚团队**：招募编译器后端/寄存器分配方向的工程能力，目标是把热路径差距从约 229 倍压缩到可对外宣称"接近或反超 C"的量级，这是产品可信度的技术前提。
2. **UniMaker 产品化与公测准备**：补齐 1:1 功能缺口、打通鸿蒙端、建立公测所需的监控和反馈闭环。
3. **安全与合规审计**：自研加密/网络协议栈虽然带来性能优势，但需要第三方安全审计来建立企业客户的信任基础，这是自研路线必须承担的额外成本。
4. **生态与开发者关系**：语言开源后的社区运营、文档、开发者布道，为长期生态积累做铺垫。

具体融资金额和阶段目标需要结合真实的团队规模扩张计划和第三方市场数据在后续版本中补充，本版本不做未经验证的数字承诺。

## 十、风险与对策

**技术风险（如实披露，不粉饰）：**
- **零 C 依赖尚未完成**：Cheng 目前仍依赖一个 C 实现的冷启动运行时/解析器兜底，"完全自主的系统语言"这个叙事在对外宣传时需要谨慎，避免夸大为"已经没有 C 代码"。对策：按既定路线图持续推进冷路径覆盖，每一步都有回归门禁背书，不因赶进度跳过验证。
- **热路径性能差距仍大（约 229 倍）**：这是 beat-C 叙事能否兑现的最大不确定性，深层优化（寄存器分配、并行代码生成）技术难度高，此前多轮尝试的收益低于预期（例如任务级并行化实测只带来约 1.03 倍提升，被判定为"死杠杆"）。对策：聚焦已被验证有效的方向（增量编译、结构性算法降阶），对已证伪的路径不再重复投入。
- **生态冷启动风险**：一门新语言 + 一个新制作器同时冷启动，开发者和创作者的双重获客难度高于单一产品冷启动。对策：先以 Cheng 语言的技术硬指标（自举、性能）吸引系统程序员社区背书，再借助 UniMaker 的具体可用场景（秒发秒开视频/内容分享）触达创作者群体，两条获客路径不完全重叠，互相独立验证。
- **自研安全栈的审计负担**：自己实现加密和网络协议意味着不能简单援引 OpenSSL 等第三方库的安全声誉，任何漏洞都要自己扛。对策：公测前完成第三方安全审计，不带着未审计的自研加密栈进入生产。

**商业风险：**
- 商业模式（订阅+企业版+生态分成）目前没有真实付费用户验证，存在"技术很硬但没人为此付费"的风险。对策：公测阶段优先验证免费层到付费层的转化率，再决定资源投入优先级，不在没有验证前扩大企业版销售团队规模。
