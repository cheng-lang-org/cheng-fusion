| `return x` 假返回 0 | `parse_return` 扫到已有 CBR 误判为 return 表达式 | 扫描边界从当前 block 扩展到全局 | ✅ 已修复 | `parse_return` 扫描边界已限制为解析后新增 blocks |

### 规避模式总结

1. **大返回值避让**: 大结构体返回值容易触发 cold ABI 污染；优先用 `out-param` (`fn Fn(args, out: var T)`) 或返回 JSON 字符串
2. **provider 隔离**: 不稳定符号路径优先走 C provider (`@importc`)，不暴露为 Cheng 标准库符号供二级 import 拉入
3. **函数粒度控制**: 超过 60 block/2000 指令的函数在 cold codegen 中易崩溃；拆为命名辅助函数
4. **AVOID 值参传递**: 除 `int32/str/bool` 外的复合类型值参不稳定；一律用 `var T` 借用
5. **const 替代**: ~~const block 中的 str 常量不可用；改为函数内 `let x = "..."` 局部绑定~~ 已修复：`parse_const_member_line` 现在正确处理 str 类型和字符串字面量 RHS
6. **二级 import 显式 touch**: cold provider system-link 可能漏掉二级 import 的业务符号；对应 smoke 必须显式 import/touch 所有依赖模块
7. **独立 OUT_DIR**: 多个 SQLite smoke 共享输出目录会导致 fixture 污染；每个 smoke 使用独立 `OUT_DIR` 和 `TMPDIR`

### import std/strings 和 std/strutils 兼容性

`std/strings` 和 `std/strutils` 在当前 cold 编译器中表现出以下兼容性问题：

1. **strings.ConcatStr**: 必须作为内建字符串拼接降到 BodyIR；Fmt 与 strutils.Join 都依赖它。直接调用会被编译为错误的多参数 ABI 或空返回
2. **strutils.Contains**: 拉入 `_Contains` 外部符号，当前 provider 未导出。改用 `protocol/wire.RustCsgContains` 手写 contains
3. **strutils.Replace**: 经普通 Cheng 函数符号 `_Replace` 调用，返回 str 必须按 ARM64 `x8` 隐式返回槽实现；按 `@importc` out-pointer ABI 会在 `Replace` 内读错参数并段错误
4. **strutils.Join**: 依赖 `ConcatStr` 内建拼接；多参数场景当前不稳
5. **std/os.ReadFile**: 当前 bridge 会丢 Cheng str 长度/元数据，表现为偶发空读或字段污染。生产切片走 provider-backed `RustCsgReadFile` (`config/home.cheng`)

**兼容策略**: 能用 provider 符号的先用 provider；能拆成手写字符串操作的不依赖标准库闭包；必须用标准库时确保对应函数签名和 ABI 已被 cold compiler 正确支持。

### 工程发现 (Engineering Discoveries)

以下是在 codex 开发过程中积累的工程经验，在正式代码和测试 harness 中已验证：

- `tools/cold_regression_test.sh` 的验收必须解析内部 summary 和 FAIL 行，不能只看 shell exit code。正式 artifact 历史完整结果曾记录 `1910 passed, 0 failed` 与 `1929 passed, 0 failed`；当前可定位原始日志为默认 `1502 passed, 0 failed`。v12 候选快速定位 run 已出现 87 个失败，不能刷新正式 artifact；`rv_all_docker_unavailable` 是环境 SKIP，不再当失败。
- 主仓冷回归脚本已改为优先使用 `$TMPDIR`/`COLD_REGRESSION_WORK_ROOT`，避免 `/tmp/ct_*`、`/tmp/cheng_cold`、`/tmp/ct_bd_ws`、`/tmp/ct_nightly` 这类固定路径继续放大 macOS 新可执行文件签名/dyld 瞬态问题。后续新增用例必须保持这个约束。
- 主仓冷回归脚本的高耗时批量段已受控并行化：默认仍串行，显式 `COLD_REGRESSION_JOBS=N` 才并发；zero-regression 内层强制 `COLD_REGRESSION_JOBS=1`；`CHENG_COLD_SKIP_ZRG=1` 只用于失败聚类，完整验收不能跳过 zero-regression。v16 生成版曾收敛到唯一失败 `mem_limit_large_5_under_256mb`，该失败已由 v22 候选修掉。
- `mem_limit_large_5_under_256mb` 的真实根因不是单个源码文件太大，而是 cold import 收集做了重复工作：`cold_collect_transitive_imports_rec` 每进入一个 transitive module 又调用一次 `cold_collect_imported_function_signatures(symbols, sub_source)`，反复扫描直接 import 并在 arena 中分配重复 qualified signature；同时 `cold_collect_import_module_types` 用完整 `symbols_new` 做本地 type scan，每个 import 预分配 4096 个 `FnDef`，约 8MB 级浪费。v22 修复为 type-scan 小符号表，并删除递归子模块的重复 imported-signature 扫描。快速定位回归结果 `1922 passed, 0 failed`，完整不跳 ZRG 回归结果 `1923 passed, 0 failed`，`gate_main` RSS 约 400MB；下一步是 backend driver 自举收敛和正式 artifact 刷新。
- shell harness 里不能把启动后台服务的函数放进命令替换并让后台进程继承 stdout；`MOCK_PORT=$(start_mock ...)` 会等 stdout pipe 关闭，后台 app-server 又在等客户端请求，形成死等。后台服务 stdout/stderr 必须重定向到文件，端口通过 portfile 传递。
- exec event loop 不能把 `item/completed` 当 `item/started` 处理。`item/completed` 的 `item` 可以只有 `id/type`，没有 `content`；读取 `content` 必须只发生在 started/full item 场景，用 optional raw value，缺失不能触发 `missing json field: content`。
- SQLite smoke 失败时必须打印 case 名、fixture path、run cwd、fixture 文件和 threads 表摘要；只报 `resume --last found no thread` 信息量不够，无法区分 SQL 数据缺失、cwd 归一化失败和 provider 字段污染。
- `resume --last` 的 SQLite full-run 不稳不是业务查询语义错误：表中目标 row 和 rollout 文件都存在，单独 by-id/rollout reader 可过。真实触发点是生成版 driver 对动态 page `rows[]`/跨 helper row 字段承载不稳；修法不是 retry，而是删掉重复循环，统一复用 `RustCsgExecResumeSqliteLookupLastFromParams`，并在该函数内用动态 offset 标量行查询逐候选匹配。targeted `run_exec_resume_lookup_sqlite_smoke.sh`、relfacts smoke 和刷新后的 full current gate 已通过。
- TUI oracle inventory 的验收必须读真实文件并校验结构，不能只用 shell `find` 数量。当前 smoke 已在 Cheng 侧读取 `.snap`/frame 内容，并把合法 `--- ` insta header 变体纳入解析。
- cold transitive import 的 path visited 只能用于递归剪枝，不能用于跳过 alias 物化。同一源文件若先被业务入口按 `exec_plan` 引入，又被配置模块按 `plan` 二次引入，少物化一个 alias 会让 `plan.RustCsgExecPlan` 缺失，字段访问退化到同名字段的错误 object layout，最终表现为 CLI/app-server 段错误。
- imported function signature 的参数 ABI 需要二次 refine。直接收集签名时，参数类型依赖的 transitive object 可能尚未进入符号表，调用点会把大型 object 值参当成 opaque/小对象传递；callee body 已按真实 object layout 生成时就会读错 `x0`。本轮用 `cold_import_param_size_smoke` 锁定旧候选运行 `SIGSEGV(139)`、新候选通过。
- app-server `command/exec` 的 streaming/tty 不能用“先跑完再返回 buffered stdout/stderr”冒充 Rust `command/exec/outputDelta` 通知。当前已闭合 `dangerFullAccess/readOnly/workspaceWrite` stdout/stderr 多帧切片；stdio JSON line 下 `streamStdin`、`command/exec/write` 和 `command/exec/terminate` 已闭合真实 stdin/control 切片；单独 `streamStdin` 已按 Rust 口径保留 buffered final stdout/stderr 且不发 `outputDelta`；WebSocket 主动 pump、stdout/stderr-only terminate、进程组 kill、direct/Seatbelt `tty:true` PTY 输出和 `resize` 已闭合；缺 `processId` 的文案必须对齐 Rust 测试。
- cold 三元表达式 lowering 必须把分支内部表达式产生的 `expr_resume_block` 作为分支出口，而不是固定从原始 true/false block 跳 outer join；否则嵌套 `return cond ? (a ? b : c) : d` 会生成断裂 CFG，新 Mach-O 运行时跳到坏地址。回归已用 `cold_return_ternary_smoke` 锁住 plain/nested then/else 四条路径。
- app-server `thread/start` 不能只补 request sequence 或返回假 id。Rust 真值是先创建 thread、返回 `ThreadStartResponse`，再发 `thread/started`；`Thread.name` 的 None 序列化为 `null`，`threadSource` 要保留；WebSocket `thread/started` 是 server notification 广播，但订阅只属于发起连接。本轮 smoke 已锁住 response、notification、SQLite row 和 unsubscribe 隔离。`thread/fork` 基础 lifecycle 已在后续切片闭合；完整 core turn loop 和 live token usage 仍不得从 `thread/start` 或 `thread/fork` 结果外推。
- app-server `turn/start` 不能用 `thread/start -> turn/start` request 序列冒充 runtime。Rust 真值是 response 先返回 `TurnStartResponse { turn }`，turn 初始为 `items=[]`、`itemsView=notLoaded`、`status=inProgress`、可空时间/error 字段为 `null`；随后 core listener 把 `turn/started` 只发给订阅该 thread 的连接。Cheng 当前只闭合 turn 创建响应和 `turn/started` 订阅 fan-out，不宣称真实模型执行、`turn/completed`、item delta 或 token usage replay。
- app-server `turn/steer` 不能发假的 `turn/started` 或 `turn/completed`。Rust 真值是校验 active turn 与 `expectedTurnId`，成功只返回 `TurnSteerResponse { turnId }`；没有 active turn 返回 `no active turn to steer`，mismatch 返回 ``expected active turn id `{expected}` but found `{actual}```，两者都是 `-32600`。Cheng 当前只闭合 active-turn precondition 和 response，不宣称追加输入已经进入真实模型执行流。
- Responses SSE 失败事件不能静默吞掉后再报 `ended before response.completed`。`response.failed`、`response.incomplete`、`error` 是模型流语义事件，app-server 必须生成结构化 failed turn；没有 assistant text 时也不能补空 `agentMessage`。当前 Cheng live/batch parser 已按该口径输出 `turn/completed` failed，并已按 Rust `CodexErr::to_codex_protocol_error` 输出 v2 camelCase `codexErrorInfo`；剩余是 retry/willRetry 和 stream disconnect 对象型错误。
- app-server dynamic tool 路径没有 `serverRequest/resolved`。Rust 真值是 `dynamicToolCall` `item/started` -> server request `item/tool/call` -> client response -> `dynamicToolCall` `item/completed`；失败也通过 item status `failed` 表达，不发 resolver notification。回模型时单个 `inputText` 是 `function_call_output.output` 字符串，多项或图片才是 content array，图片必须带 `detail: "high"`。
- dynamic tool client 响应的三类异常不能混写：JSON-RPC error 进入 Rust waiter 后转成 failed item，contentItems 是 `inputText("dynamic tool request failed")`，follow-up output 是同名字符串；result shape 反序列化失败转成 `inputText("dynamic tool response was invalid")`；JSON-RPC frame 缺 `result` 且无 `error` 在 transport 层被丢弃，请求继续 pending，不会发 completed/failed，也不会 follow-up。
- live turn 期间读取客户端 dynamic tool response 必须共享外层 transport buffer。stdio 写端是 stdout fd 1，读端是 stdin fd 0；如果 `turn_event_loop` 自己建 buffer，会丢 Content-Length/JSON line 半帧。多 WebSocket 只能读预期响应所属 fd，不能遍历 subscriber fds 抢读其它连接的 request；`item/tool/call` 发给 requester，`item/started/item/completed/turn` 通知仍按 thread subscriber fan-out。
- reasoning event 方法名不能沿用旧草案 `item/reasoningSummaryText/delta`/`item/reasoningText/delta`。Rust 当前 app-server protocol 明确是 `item/reasoning/summaryTextDelta`、`item/reasoning/summaryPartAdded`、`item/reasoning/textDelta`，字段是 `summaryIndex/contentIndex` camelCase；completed item 的 `summary/content` 已经是字符串数组，不是 OpenAI 原始 `{type,text}` 数组。
- `parallel_tool_calls` 不是 dynamic tool 自己的元数据，也不是 app-server v2 dynamic tools 字段；Rust 请求层来自 `ModelInfo.supports_parallel_tool_calls`，本地执行层另有 per-tool read/write 并行锁。当前 Cheng 只闭合请求体布尔字段；统一 tool scheduler、read/write 锁、MCP read-only/server opt-in 并行和 `OutputItemDone` 立即启动 tool future 仍是后续缺口。
- Cheng cold 路径里 `var i = p` 这类推断局部在数组/object 扫描中可能表现成别名污染，循环推进 `i` 会把 `p` 一起推进，导致 `SliceBytes(arrayJson, p, ...)` 只切到 `}`。关键解析循环用显式类型复制：`var p: int32 = ...`、`var i: int32 = p`。
- app-server command approval 和 dynamic tool 的 resolver 语义不同：`item/commandExecution/requestApproval` 必须等客户端 JSON-RPC decision，提交 same-process core `exec_approval` op，dispatch 后发 `serverRequest/resolved`，再继续 SSE；`item/tool/call` 不发 resolved。审批 request 发出后如果提前继续 assistant delta，就是错的。
- Cheng cold 路径里 `let requestId = requestIdCounter` 这类从 `var` 参数拷贝出的局部在后续 `requestIdCounter = requestIdCounter + 1` 后可能表现成被污染，导致服务端发 `id:0` 却等待 `id:1`。需要按动态工具路径写成 `var requestId: int32 = requestIdCounter`，再用该稳定副本构造 request、pending 和等待响应。
- app-server file-change approval 走当前 v2 `item/fileChange/requestApproval`，不是 legacy `applyPatchApproval`。Responses core item type 是 `apply_patch_approval_request`，app-server request params 用 camelCase `grantRoot`；core submission 是 `patch_approval`，id 用 patch `call_id/itemId`，不带 `turn_id`。mock 输入匹配不能用宽子串 `"approval flow input"`，否则 `file approval flow input` 会误走 command approval 分支。
- MCP runner approval 不能靠 `exec_approval`/`patch_approval` 工具假批准。Rust 关键路径是 app-server 发 `item/*/requestApproval`，MCP server 发 outbound `elicitation/create`，client 回 `result.decision`，原 `tools/call` 继续。当前 Cheng 已闭合同一 stdin buffer 内的 runner 切片；真实 app-server same-connection decision submission 和逐帧交互 stdin 仍要单独闭合，文档不能把 runner smoke 外推成完整 approval runtime。
- MCP runner approval resolve 的测试必须让 app-server mock 在收到 `serverRequest/resolve` 前保持 stream pending；否则 client 回 `elicitation/create` 后由测试侧直接写 flag 放行，会绕过 app-server/core submit 关键路径。resolve body 必须带 `threadId/requestId/kind/itemId`，command approval 还必须带 `turnId`，否则 app-server 应 hard-fail。
- cold import const scanner 必须先剥离行内注释再解析 RHS；`= 1 # bit 0` 和 `= 23 // comment` 都是合法 typed const，字符串 `"value#ok"` 内的 `#` 必须保留。否则 alias-qualified const 会表现为 unknown qualified identifier，TUI render attr 常量就是回归点。
- `CURRENT_SKIP_MCP=1` 是验证选择口径，不是产品完成口径。开启时必须同时跳过直接 MCP smoke、MCP oracle/relfacts 和依赖全量 MCP evidence 的聚合项；否则会出现实际非 MCP 全绿但 manifest/translation-core 因缺 MCP evidence 假红。
- `PRODUCTION_SKIP_MCP=1` 必须和 current skip 同口径：顶层 production gate 跳过 MCP product entries 与 `translate_manifest_compile`，TUI renderer production suite 只跳过 MCP 命名 renderer；summary 必须报告真实 verified/skipped 数量。不能在 skip 分支输出“115 support smokes executed”或“MCP server verified”这类已跳过内容。
- `host_provider.c` 不能合并成“纯 Cheng 方案”的一部分；它只能继续作为 retired hard-fail sentinel。真实迁移路径是把能力搬到 `src/core/runtime/*provider*.cheng`/`std/*`，再用 `--link-providers` 做 runtime provider closure。`std/os.ReadFile` 文件读取独立 smoke 已通过 `cold_runtime_provider_system_link`，但全局替换 `home.RustCsgReadFile` 会让主 app-server 在 `completion/chat` 后崩溃，所以不能把独立 runtime proof 外推为 app-server 全局 provider 化完成。
- Darwin provider system link 不能再用 `/usr/bin/cc` 或 `/usr/bin/libtool`；这些 wrapper 会调 Xcode selector 并卡在 `xcodebuild -find clang/libtool/otool`。冷编译器、app-server smoke 和 current gate 共享 provider cache 必须固定 CommandLineTools `cc/libtool` + 显式 SDK，缺失就 hard-fail。
- CLI/exec/TUI/login 产品 smoke 不能依赖 current gate 外层 `cc` shim；targeted 运行时没有该 shim。已统一 source `codex/support/darwin_clt_toolchain.sh`，用 `rust_csg_cc` 编译 provider，targeted CLI/exec/TUI/login 入口均通过。
- TUI resume picker 不能只靠 17 个静态 Rust snapshot 算 runtime 进展；还必须证明真实 state DB 行能进入同一 renderer、产出 Rust `SessionSelection`，并按 Rust keymap 做状态迁移和 loop 内核。`tui/session_picker.cheng` 已闭合 SQLite `threads` -> display preview/name/cwd/time -> comfortable/dense/footer 文本渲染 -> resume/fork selection target -> key/event reducer -> scripted loop，targeted smoke 用真实 sqlite provider 验证排序、cwd filter、selected thread、`kind/threadId/path/displayLabel`、archived/empty first_user_message 排除，以及 navigation/search/clear/density/effect/exit/start-fresh/ctrl-d no-op、多键序列到最终 selection/exit/start_fresh；root `codex resume/fork` 仍保持 78，直到 raw terminal event stream、cwd handoff 和 App 主循环闭合。
- 纯 Cheng provider 迁移不能只看“函数已搬过去”。`RustCsgAbsI32`、`RustCsgPopCount`、bit31、`RustCsgNextPowerOfTwo` 和 hash wrap 都有 C 版边界语义；cold 当前对 `int32(-2147483648)` 转换和大常量 `% 4294967296` 不稳，稳定写法是显式构造 `int32(-2147483647) - int32(1)`，hash wrap 用有限循环折回 32 位范围。`run_string_ops_provider_smoke.sh` 已锁 33 个 string/math/bit provider 的行为和 provider object 编译。
